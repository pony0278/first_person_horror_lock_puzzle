# F0 手機測試報告 — 自動化階段

> 對象：`f0_door_prototype_v28.html`
> 日期：2026-08-06
> 方法：Playwright + Chromium（WebGL 2.0），模擬 iPhone / 中階 Android 的視窗、DPR、觸控與自動播放政策
> 重跑方式：見 `tools/devicetest/README.md`

## 這份報告能證明什麼、不能證明什麼

**能**：版面幾何、觸控命中區、事件處理有無、瀏覽器政策（自動播放、縮放）、WebGL context 行為、
以及所有可由程式碼算出的視覺量值。這些在模擬視窗下與真機一致。

**不能**：真實 GPU 的 FPS、發熱、iOS Safari 網址列收合行為、戶外可辨識度、實際觸感。
本環境只有 SwiftShader 軟體渲染（實測 5~7 FPS），**該數字不可拿來當效能結論**。
這些留在 `f0_device_test_checklist.md`，需要人拿真機跑。

## 阻擋級（會讓實機測試白跑，建議測試前處理）

### B1. 手機橫向的上下分區反了：下方面板吃掉 42~61%

設計文件 §4 訂的是上方 65~70%、下方 30~35%。實測：

| 裝置 | 上方視野 | 下方面板 | 面板佔比 |
| --- | --- | --- | --- |
| iPhone 13 橫向 844×390 @3x | 227px | 163px | **41.8%** |
| iPhone SE 橫向 667×375 @2x | 212px | 163px | **43.5%** |
| 中階 Android 橫向 780×360 @2.75x | 197px | 163px | **45.3%** |
| 同上但 DPR=1（桌機小窗 / 部分裝置） | 152px | 238px | **61.0%** |
| iPhone 13 直向 390×844 @3x | 557px | 287px | 34.0%（正常） |

**成因（已驗證，非推測）**：`#panel` 是 `flex: 0 0 34%` 且 `min-height:auto`，
所以它的實際高度是 `max(34% 基準, min-content)`。而 `#pins` 的 min-content 包含
`#cut` canvas 的 **內建像素高度**（`cutCanvas.height = $pins.clientHeight × min(dpr,2)`，
`f0_door_prototype_v28.html:1999`）。百分比高度在 min-content 計算時解不出來，就退回內建尺寸，
於是形成回授迴圈並鎖死在一個定值：

```
DPR≥2 → 收斂在 pins=75px、canvas.height=150 → panel 163px（不隨視窗高度變）
DPR=1 → 收斂在 pins=150px、canvas.height=150 → panel 238px
```

視窗高 300 / 360 / 420 都得到同一個 163px，證實它已脫離 34% 的控制。

**為什麼你在桌機沒發現**：1920×1080 時 34% = 367px > 238px，基準值勝出，比例正確。
這個 bug 只在視窗矮的時候咬人 —— 也就是唯一的目標姿勢，16:9 手機橫向。

**驗證過的修法**（在頁面上熱套後量測，三種 DPR 都回到 34.0%）：
`#panel { min-height: 0 }` + 讓 `#cut` 用 `position:absolute; inset:0`（`#pins` 加 `position:relative`）
脫離 min-content 計算。

> 注意：單獨套這個修法會讓面板縮到 133px，剖面圖更擠 —— 見 B2，兩者要一起解。

### B2. 撞針高度差在手機橫向只剩 3.5px，設計文件 §7 的核心主張不成立

`drawCutaway()` 全部用 `h = $pins.clientHeight` 等比縮放，所以狀態差隨面板高度線性縮水：

| | 桌機 1080p<br>(pins 279px) | iPhone 直向<br>(pins 199px) | **手機橫向**<br>**(pins 75px)** |
| --- | --- | --- | --- |
| idle → partial（推錯，頂到 40%） | 12.8px | 9.2px | **3.5px** |
| idle → set（固定） | 32.1px | 22.9px | 8.6px |
| partial → set | 19.3px | 13.7px | 5.2px |
| set → falseSet（假針） | 7.8px | 5.6px | 2.1px |

設計文件 §7：「錯的針推到約 40% 就頂住／對的針順暢上到 100%……**前兩者靠針的高度即可分辨，
完全不依賴聲音**。」在手機橫向，那個「高度」是 3.5 CSS px。

`set → falseSet` 只差 2.1px 是**刻意的**（§9：下方無法分辨真假，要靠上方鎖芯），這條沒問題。
出問題的是 `idle → partial` —— 那是玩家判斷「我剛剛推錯了」的唯一視覺依據。

**而且同時，聲音那條路也是斷的**（見 B3），所以手機上兩條回饋路徑一起失效。
這直接壓到驗收標準 #3（假針能被識破嗎，5 成／3 局），也可能拖累 #2（死亡時知道原因嗎，8 成）。

若在這個狀態下做 5~8 人驗收，標準 #3 沒過會分不清是「回饋強度要調」還是「手機上根本看不到」。

### B3. iOS Safari / Chrome Android 上完全沒有聲音

`beep()` 在 `f0_door_prototype_v28.html:1937` 才惰性建立 AudioContext，
而**第一個呼叫者是開場演出**（`beep('tap')` / `beep('thunk')`），不是使用者手勢。
全檔案沒有任何 `actx.resume()`。

開啟真實自動播放政策（`--autoplay-policy=document-user-activation-required`，等同 iOS Safari
與 Chrome Android 的行為）實測：

```
載入後（intro 已呼叫 beep，無使用者手勢）: suspended
使用者觸控撬鎖面板之後:                    suspended   ← 不會自己恢復
程式碼中是否有 actx.resume():              false
```

在無自動播放限制的桌機 Chromium 下則是 `running` —— 所以這在你的開發機上看不出來。

設計文件 §9「聲音是加速器，不是必需品」讓這不至於是致命傷，但 B2 + B3 疊起來，
手機玩家的回饋通道剩下鎖芯角度（8~10°，在 227px 高的視野裡）這一條。

## 高（不阻擋測試，但要記進 F0.1）

### H1. 沒有 safe-area 處理

全檔案沒有任何 `env(safe-area-inset-*)`（`viewport-fit=cover` 有設，見 line 5，所以內容確實會鋪到瀏海底下）。實測重疊：

- **iPhone 13 橫向**：撬鎖區與「全部洩壓」鈕左緣在 x=12，瀏海區到 x=47 → 最左邊那支針被瀏海壓到
- **iPhone 13 橫向**：「全部洩壓」鈕下緣 378px，home indicator 區從 369px 起
- **iPhone 13 直向**：「全部洩壓」鈕下緣 832px，home indicator 區從 810px 起

橫向時最左側撞針同時吃到瀏海遮擋和邊緣返回手勢區，是四支針裡最難按的一支。

### H2. 切到背景，隱藏計時器照跑

`R.elapsed = (performance.now() - R.t0) / 1000`（line 2519）是牆鐘時間，
而全檔案沒有 `visibilitychange` 處理。實測 3 秒背景 = 吃掉 3.0 秒。

20 秒的限時下，一則通知橫幅或誤觸 home 就是 15~25% 的回合時間。
設計文件 §6 的第一原則是「怪物必須誠實」—— 玩家不會知道自己是被通知殺死的。

> 順帶：開場演出用的是 `dt`（`clock.getDelta()` 上限 0.05s，line 2447），
> 計時器用的是牆鐘。兩套時間基準並存，低幀率時會對不上（見 M1）。

### H3. 沒有 WebGL context loss 恢復

設計文件 §2 把這條列為「第一週內驗證」的已知風險並要求「實作恢復流程，避免黑畫面」。
目前沒有 `webglcontextlost` 監聽。實測觸發 `WEBGL_lose_context.loseContext()` 後
2 秒 `isContextLost=true`，畫面停在最後一幀，不會恢復。

手機切分頁、切 App、記憶體壓力都可能觸發。

### H4. 「全部洩壓」鈕 66×27px，低於 44×44

所有測試機型都一樣（尺寸由字級決定，不隨視窗變）。
設計文件 §4 把洩壓列為「必要」機制 —— 玩家識破假針後沒有它會卡死到超時。
27px 高在橫向又貼近 home indicator（H1），是整個介面最難按的元素。

撞針本身的命中寬度沒問題（橫向 154~199px、直向 69~75px，全部過關）。

### H5. 三份資源全部靠 CDN，離線與弱網直接白畫面

`<script type="importmap">` 指向 `https://unpkg.com/three@0.160.0/build/three.module.js`（line 110）。
沒有 fallback、沒有載入失敗處理。CrazyGames 要求「玩家一進來就在 gameplay 裡」（§2），
unpkg 在部分地區與行動網路下的延遲會直接違反這一條，且平台上架時本來就要自帶資源。

（本次測試是把 three.js 抓到本地才跑得起來 —— 這個環境的網路代理擋掉了 unpkg，
正好示範了失敗長什麼樣：完全白畫面，無任何提示。）

## 中（觀察，不一定要動）

### M1. 幀率低於 20 FPS 時，開場演出會等比拉長

開場是 `dt` 驅動且 `dt = min(clock.getDelta(), 0.05)`，所以幀時間超過 50ms（<20 FPS）時
演出會照比例變慢。設計值 2.2+1.3+0.95 = 4.45 秒，本環境（5~7 FPS）實測 8.5~25 秒。

**30 FPS 以上不受影響**（幀時間 33ms < 50ms 上限），所以這只是低階機的風險，不是普遍問題。
但真的掉到 20 FPS 以下時，玩家會先看一段拖沓的開場，這與 §2「一進來就在 gameplay 裡」衝突。

### M2. 直向沒有任何處理

設計文件 §4 訂的是 16:9 橫向。直向下版面不會壞（比例反而正確、撞針也夠寬），
但視野是 390×557 的直立框，走廊透視與暗角都不是為這個比例設計的。
目前沒有鎖定方向，也沒有「請轉橫」提示。要決定是支援還是擋掉。

### M3. 上方點一下（非長按）就會觸發回頭

`view` 的 `pointerdown` 直接 `look.target = 180`（line 2399-2404），沒有長按或拖曳門檻。
畫面提示寫的是「按住畫面 = 回頭」，但設計文件 §17 的 F0 規格寫的是
「按住向下拖曳 = 回頭」，§4 則是「上方按住＋向下拖曳」。

實作比規格寬鬆。這本身可能是刻意簡化，但它會影響驗收標準 #1（8 成玩家第一局內至少回頭一次）
的解讀 —— 誤觸也會計入「主動回頭」。第 17 節更新時要一起對齊。

### M4. 效能面的靜態盤點（真機才能下結論）

| 項目 | 數值 | 判讀 |
| --- | --- | --- |
| 每幀像素 | 0.57~0.77 MPx（pixelRatio 上限 2.0） | 不是瓶頸 |
| 動態光源 | 6 盞（4 PointLight + 1 SpotLight + 1 HemisphereLight） | **主要成本**，MeshStandardMaterial 每個受光片段要算 6 次 |
| 陰影 | 全關（`flash3d.castShadow = false`） | 好 |
| 自訂著色器 | 3 處（暗角、滲液、水面） | 需在真機看 |
| 霧 | FogExp2 | 便宜 |
| 檔案 | HTML 144KB + three.min 656KB ≈ 800KB | 遠低於 20MB 預算 |

沒有動態解析度調降機制。中階 Android 若不到 30 FPS（§2 的下限），目前沒有退路。

## 通過的項目

- 版面無溢出、無橫向捲動（全機型）
- 雙擊不觸發頁面縮放（`touch-action:none` + viewport meta 有效）
- 撞針觸控命中寬度全部 ≥44px
- 觸控推針功能正常（實測 tap 可推針，狀態機正確轉為 partial / falseSet）
- `pointercancel` 有處理（`#pins` 與 `#view` 都有）
- WebGL 2.0 可用、canvas 正確依 DPR 建立
- 直向的上下比例正確（34.0%）
- 載入無 JS 例外（本地資源版）

## 建議的處理順序

1. **B1 + B2 一起解**（分區與剖面圖可讀性是同一個問題的兩面）
2. **B3**（一行 `actx.resume()` 掛在第一次觸控上）
3. H1、H4（safe-area + 洩壓鈕命中區，同一區塊順手做完）
4. H2、H3（`visibilitychange` 暫停計時 + context loss 恢復）
5. H5（把 three.js 內嵌或同目錄自帶）—— 上架前必做，測試前非必要（測試機有網路即可）

B1~B3 未處理前做 5~8 人驗收，標準 #3 的結果無法解讀。
